# elm-daisyui: daisyUI → Elm typed composition layer

Read `SPEC.md` for the full handoff spec. This file records the conventions and decisions that
downstream work must follow so that independently written parts fit together.

## What this is

An Elm 0.19.1 package (`src/Daisy/*`) where a developer composes daisyUI views only through a
closed view tree (`Daisy.Tree`), rendered by `Daisy.Render`. The type checker plus the test
suite guarantee: no contradictory modifiers, no invalid nesting, overlays in one fixed layer,
max 5 sections and exactly one primary CTA per page. daisyUI CSS is used unchanged.

## GitHub Pages

The demos are published at https://alexbruf.github.io/elm-daisyui/, a project site, so they are
served from `/elm-daisyui/` there and from `/` everywhere else (`vite dev`, `vite preview`,
Playwright). One mechanism handles both:

- `demo/vite.config.js` reads `VITE_BASE` (or `BASE_PATH`) into Vite's `base`, defaulting to `/`.
  `.github/workflows/pages.yml` sets it from `actions/configure-pages`' `base_path` output.
- Vite exposes that value to the bundle as `import.meta.env.BASE_URL`; `demo/src/main.js` passes it
  to Elm as the `basePath` flag.
- `demo/src/BasePath.elm` has the only two operations on it: `strip` takes the prefix off an
  incoming `Url.path` before `routeFromUrl` matches, and `join` puts it back on every sidebar/navbar
  `href` and every `Nav.pushUrl`. The four routes stay base-free (`/`, `/analytics`, `/settings`,
  `/theme`).
- GitHub Pages has no SPA fallback, so the build copies `dist/index.html` to `dist/404.html` (a
  small Vite plugin in `demo/vite.config.js`). Pages serves 404.html for any path with no file,
  which is every deep link into the router.

## Docs site

`demo/`'s `bun run build` is `vite build` followed by `bun ../tools/build-docs-site.js dist`, so
every build (local and Pages) also writes a static documentation site to `demo/dist/docs/`:

- One page per committed markdown file — README.md, `docs/placement.md`, `docs/tree-decisions.md`,
  `docs/demo-findings.md`, `docs/e2e-findings.md`, `fixtures/rejected.md`,
  `fixtures/schema-diff.md` — plus a generated contents page at `docs/index.html`. Nothing in the
  output is hand-written HTML; the generator renders the markdown with `marked` (a root
  devDependency) into one daisyUI layout (`navbar` + `article.prose`, `data-theme="light"`).
- The pages link the demo's own hashed `assets/*.css`, found in the output directory at build time,
  so daisyUI styles them. The three utilities the layout needs that the demo itself never emits
  (`max-w-none`, `p-8`, `shadow-sm`) are safelisted with `@source inline(...)` in `demo/app.css`,
  because Tailwind scans before the docs pages exist.
- Relative markdown links are rewritten: to `<name>.html` when the target is one of the rendered
  files, otherwise to the file on GitHub. Headings get GitHub-style ids so `#anchor` links work.
- The script reads the same `VITE_BASE` / `BASE_PATH` as `demo/vite.config.js`, so its stylesheet
  and navbar URLs carry the base path.
- All three dashboard sidebars carry a `Docs` `MenuItem` pointing at `<base>docs/`. It has no `onClick`,
  and `Main.step` answers a `UrlRequest` for a path that is not one of the four routes with
  `Browser.Navigation.load`, so the browser really leaves the single-page app.

## Generated schema conventions (fixed; Tree/Render/tests depend on these)

Elm forbids two types in one module sharing constructor names, so the schema is one module per component:

- `Daisy.Schema.<Component>` where `<Component>` is PascalCase of the docs page slug (`button` → `Button`, `file-input` → `FileInput`, `mockup-code` → `MockupCode`).
- Exclusive groups (`color style size direction placement variant`) each become `type <Group> = A | B | ...` with `<group>ToClass : <Group> -> String`, e.g. `Daisy.Schema.Button.Color`, `Daisy.Schema.Button.colorToClass`.
- `modifier` and `behavior` groups become `type Modifier = ...` / `type Behavior = ...` with `modifierToClass` / `behaviorToClass` (sets: a config holds `List Modifier`).
- Constructor names: class minus the component prefix, PascalCase (`btn-primary` → `Primary`, `btn-xs` → `Xs`, `mask-half-1` → `Half1`). If stripping produces an invalid or duplicate name, fall back to the full class PascalCased. Constructors must be unique within a module.
- Each module also exposes `component : String` (the main component class), `componentClasses : List String`, `parts : List String`, and `all<Group> : List <Group>` for every generated type (needed by fuzzers and coverage tests).
- `Daisy.Schema` (aggregate) exposes `allClasses : Set String`, `exclusiveGroups : List { component : String, group : String, classes : List String }`, `parts : List { component : String, part : String }`, `componentClasses : List String`.
- `fixtures/schema.json` shape: `{ "<slug>": { "<group>": ["class", ...] } }` with the same 10 groups; browser-specific entries are dropped.

## Tree conventions

- Levels: Page > Section > Block > Leaf. Overlays only in `Page.overlays`. Exactly as in SPEC.md step 3; extend the `Leaf`/`Block` constructor lists per `docs/placement.md`.
- Every `XConfig` record has one `Maybe <Group>` field per exclusive group of that component plus `modifiers : List X.Modifier`. No `String` class field anywhere. Provide a `defaultXConfig` value for every config.
- `Daisy.Tree` defines its own `ButtonColor` that omits `Primary`; Render maps it to `Daisy.Schema.Button.Color`. The only primary button is `Page.cta`.
- Components with `part` classes take a record of parts (a part cannot appear outside its component or twice).
- `dropdown` and `tooltip` are fields on leaves, not nodes. No `Raw Html` constructor. Ever.
- **Custom views go through `Leaf.Embed` and nowhere else.** `Embed EmbedConfig (ThemeContext -> Html msg)`,
  `EmbedConfig = { height : EmbedHeight, label : String }` with `EmbedHeight = EmbedSm | EmbedMd | EmbedLg`
  (160/256/384px, fixed `Render.tokens`, never a number from the caller). `Daisy.Render` draws the
  result inside a `relative overflow-hidden w-full` box of that height, with `role="figure"` and
  `aria-label = label`, so an embed cannot overlap its neighbours, cannot escape its box and cannot
  go unnamed. It is a `Leaf`: no block, section or overlay inside it, and it cannot stand where one
  belongs (`tools/should-not-compile/Reject/EmbedAsBlock.elm`).
  The embed is themed, not classed: `Daisy.Render` hands it a
  `ThemeContext = { color : SemanticColor -> String, surface : Surface -> String, theme : Theme, radiusBox : String }`
  whose colours are `var(--color-*)` / `var(--radius-box)` strings, so the drawing follows the active
  theme with no re-render. `NoClassOutsideRender` and `NoRawSchemaStrings` still apply inside an
  embed — **no `class` attribute at all** — so inline `style` and SVG presentation attributes are how
  it paints. Embed view functions live under `demo/src/Viz/`, the only path `NoHtmlInDemo` exempts;
  `Demo.*` pages still may not import `Html`.
  The trade-off, stated once: coverage and the corpus cannot see inside an embed (it emits no
  classes), while overlap, overflow, contrast, a11y and the theme/chart-colour sweeps still can.
- `Theme` is either one of the 35 built-ins or `Custom CustomTheme` — the same 29 declarations
  daisyUI's own theme format has, every field a closed type. `ThemeName` is opaque (`themeName`
  validates `[a-z][a-z0-9-]*` and refuses the 35 reserved names; `themeNameOf` is the only way to
  reach a built-in's). `allThemes` stays the 35 built-ins. `Daisy.Themes` (generated) is every
  built-in as a `CustomTheme` value, which is what "start from a built-in" needs.
  **A `Custom` theme needs no stylesheet:** `Daisy.Render.page` writes the 29 declarations onto the
  page root as ONE inline `style` attribute (`Attr.attribute "style" (Tree.customThemeStyle t)`).
  It must be the attribute, never `Html.Attributes.style` per property — `elm/virtual-dom` applies a
  style node with `element.style[key] = value`, which silently ignores a `--*` name. See
  `docs/tree-decisions.md`, "Custom themes and the generator page", section 3.
- `Leaf.Calendar` delegates to `alexbruf/elm-cally` (a pure-Elm port of the Cally web component: same
  markup, same `part` attributes, light DOM, no ports). elm-cally's `Config` is built inside `Render`
  from the closed `CalendarConfig`, never exposed — the same rule `Daisy.Chart` follows for elm-charts.
  Its state lives in the app: `Daisy.Render.initCalendar*` / `updateCalendar`, `Daisy.Tree.setCalendarValue`.
  `TwoMonths` wraps its two `Month.view` grids in a container of Render's own (`grid grid-cols-1
  sm:grid-cols-2 gap-4`, all four already in `tokens`), because neither elm-cally nor daisyUI styles
  `[part~=months]` — upstream Cally leaves multi-month layout to the page. Grid, not flex: daisyUI's
  `.cally calendar-month { width: 100% }` would make flex items each claim a whole line. See
  `docs/tree-decisions.md` "Calendar via elm-cally" section 7.
- `Shell.Dashboard` renders as `drawer` + `drawer-open` at `lg:` with the sidebar panel in `drawer-side`
  and `navbar` on top. The panel is `DashboardShell = { brand, sidebar, sidebarFooter, navbar }`: a brand
  row, the `menu`, and a footer leaf pinned to the bottom. The `drawer-button` is offered at every width.
- `Section.Grid` takes a closed `GridSection`: `Columns GridConfig (List (Block msg))` for equal
  tracks, or `Spans (List (GridItem msg))` for the twelve-column band, where every cell states its
  `Span1..Span12`, holds a *list* of blocks and may lay them out as a grid of its own
  (`CellColumns`). The split is in the payload type so a spanned cell in an equal grid and a bare
  block in the twelve are both a `TYPE MISMATCH`, and `Section` keeps its five constructors.
- `Page.header : Maybe (PageHeader msg)` (`{ title, breadcrumbs, actions }`) is the page's title bar. It is
  **not** a `Section` — the five-section budget is content, and a title bar is chrome — so the shell draws
  it above the sections under both `Plain` and `Dashboard`.

## Render conventions

- All spacing/layout Tailwind tokens live in one constant table `Daisy.Render.tokens : List String` (gap, grid-cols, padding, height per size, icon size, and the two surface tokens `bg-base-200` / `shadow-sm`). RenderPurityTest asserts every emitted class is in `Schema.allClasses` or `tokens`, and `tools/render-class-audit.js` asserts every entry is a named `token*` constant with no daisyUI class in it. Before adding one, check `tests/RenderPurityTest.elm`'s `forbidden` list — `rounded-box`, `shadow-md`/`-xl` and `opacity-50` are there on purpose and that list is not to be edited to make room (`border` left it in the generator-chips pass as `tokenBorderBox`, one use site). 122 entries today: the 58 of the Nexus pass, the 18 colour tokens `Leaf.Swatch` paints a palette
  chip from, and the 24 of the charts-and-fidelity pass — `lg:grid-cols-12` plus twelve
  `lg:col-span-*` (the `GridSection.Spans` band) and `xl:grid-cols-3` (`CellColumns.CellThree`),
  `p-5` (`CardPadding.PaddingDashboard`), `self-start`
  (the `stat-figure` tile), `border-b`/`border-r`/`border-base-300` (`DashboardShell.edges`),
  `overflow-hidden` (clipping the chart tooltip's header row) and the four `daisy-anim-*` classes
  whose rules are `Daisy.Css`'s. Nothing left `forbidden` in that pass: `border` (all four sides on
  an arbitrary element) stays, because a one-sided rule on chrome the renderer owns with one use
  site is a different thing (`bg-primary` + `text-primary-content` and so on, one pair per `SwatchColor`, each with
  exactly one use site in `swatchClasses`). Those are the only *colour* tokens — everywhere else
  colour is daisyUI's component classes — and `bg-primary` left `forbidden` for that reason;
  `text-primary` did not and stays there. (`gap-6`, `text-xs` and `rounded-lg` *were* promoted out of `forbidden` into named tokens in the Nexus design pass — see `docs/tree-decisions.md` — which is the only way an entry may leave that list: it becomes one named constant with one job, never room for a sprinkled utility.)
- A `stat` tile's gutter is `p-5` (20px), not daisyUI's `1rem`/`1.5rem`: 48px of inline padding in a
  269px metric cell leaves too little for a number, its delta badge and a figure on one line.
- Surfaces are the renderer's job, not the caller's: `card` and `stats` emit `bg-base-100 shadow-sm` (a
  `stats` inside a `card` emits neither — the card is already that panel), a `stat-figure` gets a
  `bg-base-200 rounded-lg p-2` tile, the dashboard `drawer-content` and the plain `<main>` emit `bg-base-200`, and `navbar` emits `p-4` (the same gutter as the content column, so an `indicator-item` cannot overhang the viewport). daisyUI paints none of these itself; its own docs examples add them as utilities.
- **A CSS custom property is written as a whole `style` *attribute*, never `Html.Attributes.style`.**
  `elm/virtual-dom` applies a style node with `element.style[key] = value` and a
  `CSSStyleDeclaration` silently ignores a `--*` name, so the per-property form is a no-op.
  `Daisy.Render.customProperty` (`radial-progress`, `countdown`) and `Daisy.Tree.customThemeStyle`
  (a `Theme.Custom`) are the two places this comes up; both go through `Attr.attribute "style"`.
- **A `role="progressbar"` and every radio of a `rating` must carry a name.** Neither takes one from
  its content (`Daisy.Render.ratingDefaultLabel`, `RadialProgressData.ariaLabel`).
- **A control that carries an `onClick` and no `href` is a `<button>`, never an `<a>`.**
  `Browser.application` installs a document-level click listener that walks up to the nearest `<a>`,
  reads its `href` *property* (`""` for an anchor with no attribute) and sends
  `UrlRequested (External "")` — which a router answers with `Navigation.load ""`, i.e. a full page
  reload, with `preventDefault` making it look as if the click did nothing.
  `Daisy.Render.clickableHtml` is that rule, for `Tab` and for `MenuItem`.
- `Leaf.Icon` emits no daisyUI class at all, only a `size-*` token. Path data lives in `Daisy.Render.Icons`, which stays out of `elm.json`'s `exposed-modules`; `Daisy.Icon` is data only. heroicons is a `devDependency` of `demo/` used to copy the `d` attributes once — never a runtime dependency.
- Overlays render after sections, order: drawer, modal, toast, inside one fixed wrapper.
- Chart colors are `var(--color-primary)` etc. via `Daisy.Chart.SemanticColor`. Chart height is fixed per block size token.
  A bar chart's track and a hovered column's band are `var(--color-base-200)` / `var(--color-base-300)`,
  module constants in `Daisy.Chart` rather than `SemanticColor` values — a *series* must not be able to
  pick the colour of the panel it is drawn on. `Block.Chart` / `CardChild.CardChart` take an optional
  `ChartInteraction msg` keyed on the **x index**; elm-charts' `Chart.Item` never leaves `Daisy.Render`.
  The drawing is wrapped in `Html.Keyed` under a key derived from the config and the data, so replacing a
  dataset remounts the SVG and replays the CSS animation while hovering does not.

## Tooling rules

- Use `bun`/`bunx`, never npm/npx. Node scripts in `tools/` run with `bun`.
- `elm-format` everything Elm. `elm make` must produce zero warnings for `src/`.
- `tools/gen-cally-css.js` reads elm-cally's stylesheet out of `Cally.Css.stylesheet` (elm-cally 1.1.0+),
  preferring `~/.elm/0.19.1/packages/alexbruf/elm-cally/<newest>/src/Cally/Css.elm`, then the checkout at
  `~/elm-calendar/elm-cally/src/Cally/Css.elm`, then the old root `cally.css` for 1.0.0. It decodes the
  Elm triple-quoted literal and, when the checkout is present, byte-compares the result against that
  repo's `cally.css`, so a stale generated module fails rather than changing the demo silently. The
  source it used is recorded in the generated header. `elm.json` asks for `alexbruf/elm-cally 1.x`,
  which covers both. 1.1.0 is now published (package.elm-lang.org lists 1.0.0 and 1.1.0), so the
  package-cache path is the one that is used and a clean CI checkout resolves the demo's pinned
  1.1.0 from the registry with no local checkout involved.
- Playwright uses the system Chrome: `channel: "chrome"` (no browser download needed). Run headless.
- The demo bundles its font: `demo/package.json` depends on `@fontsource-variable/inter`, `demo/app.css`
  imports it and sets `@theme { --font-sans: "Inter Variable", ui-sans-serif, system-ui, sans-serif; }`.
  Tailwind 4 feeds `--font-sans` into `--default-font-family`, which preflight puts on `html`, and daisyUI
  declares no font-family of its own. Self-hosted through Vite (`dist/assets/*.woff2`), never a CDN. It is
  there so screenshots do not depend on the host's `sans-serif`; do not remove it or add a CDN font link.
- Screenshot baselines are **environment-tagged**. `e2e/lib/snapshot-tag.ts` reads `SNAPSHOT_TAG`
  (default `local`), `playwright.config.ts` uses it as `snapshotPathTemplate:
  {snapshotDir}/<tag>/{arg}{ext}`, so the sets are `e2e/snapshots/local/` (this machine, 105 images) and
  `e2e/snapshots/ci/` (ubuntu-latest). `ci.yml` sets `SNAPSHOT_TAG: ci`. `maxDiffPixels` stays 0 — never
  add a pixel tolerance to make two environments agree; add a tag instead.
- A tag with no committed baselines makes `themes.spec.ts` **skip** its 144 comparisons with a printed
  one-line instruction, rather than writing them. The chart-colour sweep (`themes.spec.ts`) and the
  contrast sweep (`contrast.spec.ts`) are pixel-free and run under every tag. Both sweeps cover 36
  themes: daisyUI's 35 plus the demo's own `Theme.Custom` (`acme`), which no stylesheet declares and
  which therefore exercises the inline-property path end to end.
- Regenerating the CI set is a manual decision: Actions -> *Update screenshot baselines* -> Run workflow
  (`update-snapshots.yml`, `workflow_dispatch` only). It commits `e2e/snapshots/ci/**` to the branch it ran
  on as `github-actions[bot]` with the default `GITHUB_TOKEN`. That push does **not** trigger other
  workflows, so start CI by hand afterwards: Actions -> *CI* -> Run workflow (`ci.yml` has a
  `workflow_dispatch` trigger for this).
- Do not write to `vendor/daisyui`. Do not hand-edit `src/Daisy/Schema*.elm`; change `tools/gen-schema.js` and regenerate.
- No `Html.Attributes.class`/`classList`/`attribute "class"` outside `src/Daisy/Render.elm`. No `Html`/`Html.Attributes`/`Svg` imports under `demo/src`.
- Ports are allowed in `demo/src` (`demo/src/Ports.elm`, a `port module` with no `Html` import) for browser APIs Elm cannot reach: the clipboard, and `CompressionStream` for the daisyUI theme-generator `#theme=` hash. `Main` is not a `port module`.
- Never `cat` or read the dotenv file directly in shell commands (a hook blocks it); there are no secrets in this project anyway.
- CI order (`tools/ci.sh`): gen-schema diff → gen-themes diff → elm make → package-docs → elm-review → elm-test → render-audit → should-not-compile → gen-cally-css → gen-daisy-css diff → demo build → css-coverage → Playwright. Any failure stops.
- `package-docs` is the `elm publish` gate: `elm make --docs=<tmp>` (every exposed module needs a module comment with `@docs` for everything it exposes) plus `elm-format --validate src`. The package name in `elm.json` must equal the GitHub repo, `alexbruf/elm-daisyui`; `tools/gen-schema.js` rewrites only `exposed-modules` and leaves the name alone.
