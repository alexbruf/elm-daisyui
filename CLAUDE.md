# elm-daisyui: daisyUI → Elm typed composition layer

Read `SPEC.md` for the full handoff spec. This file records the conventions and decisions that
downstream work must follow so that independently written parts fit together.

## What this is

An Elm 0.19.1 package (`src/Daisy/*`) where a developer composes daisyUI views only through a
closed view tree (`Daisy.Tree`), rendered by `Daisy.Render`. The type checker plus the test
suite guarantee: no contradictory modifiers, no invalid nesting, overlays in one fixed layer,
max 5 sections and exactly one primary CTA per page. daisyUI CSS is used unchanged.

## GitHub Pages

The demos are published at https://alexbruf.github.io/elm-daisyui/, a project site, so they are
served from `/elm-daisyui/` there and from `/` everywhere else (`vite dev`, `vite preview`,
Playwright). One mechanism handles both:

- `demo/vite.config.js` reads `VITE_BASE` (or `BASE_PATH`) into Vite's `base`, defaulting to `/`.
  `.github/workflows/pages.yml` sets it from `actions/configure-pages`' `base_path` output.
- Vite exposes that value to the bundle as `import.meta.env.BASE_URL`; `demo/src/main.js` passes it
  to Elm as the `basePath` flag.
- `demo/src/BasePath.elm` has the only two operations on it: `strip` takes the prefix off an
  incoming `Url.path` before `routeFromUrl` matches, and `join` puts it back on every sidebar/navbar
  `href` and every `Nav.pushUrl`. The three routes stay base-free (`/`, `/analytics`, `/settings`).
- GitHub Pages has no SPA fallback, so the build copies `dist/index.html` to `dist/404.html` (a
  small Vite plugin in `demo/vite.config.js`). Pages serves 404.html for any path with no file,
  which is every deep link into the router.

## Docs site

`demo/`'s `bun run build` is `vite build` followed by `bun ../tools/build-docs-site.js dist`, so
every build (local and Pages) also writes a static documentation site to `demo/dist/docs/`:

- One page per committed markdown file — README.md, `docs/placement.md`, `docs/tree-decisions.md`,
  `docs/demo-findings.md`, `docs/e2e-findings.md`, `fixtures/rejected.md`,
  `fixtures/schema-diff.md` — plus a generated contents page at `docs/index.html`. Nothing in the
  output is hand-written HTML; the generator renders the markdown with `marked` (a root
  devDependency) into one daisyUI layout (`navbar` + `article.prose`, `data-theme="light"`).
- The pages link the demo's own hashed `assets/*.css`, found in the output directory at build time,
  so daisyUI styles them. The three utilities the layout needs that the demo itself never emits
  (`max-w-none`, `p-8`, `shadow-sm`) are safelisted with `@source inline(...)` in `demo/app.css`,
  because Tailwind scans before the docs pages exist.
- Relative markdown links are rewritten: to `<name>.html` when the target is one of the rendered
  files, otherwise to the file on GitHub. Headings get GitHub-style ids so `#anchor` links work.
- The script reads the same `VITE_BASE` / `BASE_PATH` as `demo/vite.config.js`, so its stylesheet
  and navbar URLs carry the base path.
- Both dashboard sidebars carry a `Docs` `MenuItem` pointing at `<base>docs/`. It has no `onClick`,
  and `Main.step` answers a `UrlRequest` for a path that is not one of the three routes with
  `Browser.Navigation.load`, so the browser really leaves the single-page app.

## Generated schema conventions (fixed; Tree/Render/tests depend on these)

Elm forbids two types in one module sharing constructor names, so the schema is one module per component:

- `Daisy.Schema.<Component>` where `<Component>` is PascalCase of the docs page slug (`button` → `Button`, `file-input` → `FileInput`, `mockup-code` → `MockupCode`).
- Exclusive groups (`color style size direction placement variant`) each become `type <Group> = A | B | ...` with `<group>ToClass : <Group> -> String`, e.g. `Daisy.Schema.Button.Color`, `Daisy.Schema.Button.colorToClass`.
- `modifier` and `behavior` groups become `type Modifier = ...` / `type Behavior = ...` with `modifierToClass` / `behaviorToClass` (sets: a config holds `List Modifier`).
- Constructor names: class minus the component prefix, PascalCase (`btn-primary` → `Primary`, `btn-xs` → `Xs`, `mask-half-1` → `Half1`). If stripping produces an invalid or duplicate name, fall back to the full class PascalCased. Constructors must be unique within a module.
- Each module also exposes `component : String` (the main component class), `componentClasses : List String`, `parts : List String`, and `all<Group> : List <Group>` for every generated type (needed by fuzzers and coverage tests).
- `Daisy.Schema` (aggregate) exposes `allClasses : Set String`, `exclusiveGroups : List { component : String, group : String, classes : List String }`, `parts : List { component : String, part : String }`, `componentClasses : List String`.
- `fixtures/schema.json` shape: `{ "<slug>": { "<group>": ["class", ...] } }` with the same 10 groups; browser-specific entries are dropped.

## Tree conventions

- Levels: Page > Section > Block > Leaf. Overlays only in `Page.overlays`. Exactly as in SPEC.md step 3; extend the `Leaf`/`Block` constructor lists per `docs/placement.md`.
- Every `XConfig` record has one `Maybe <Group>` field per exclusive group of that component plus `modifiers : List X.Modifier`. No `String` class field anywhere. Provide a `defaultXConfig` value for every config.
- `Daisy.Tree` defines its own `ButtonColor` that omits `Primary`; Render maps it to `Daisy.Schema.Button.Color`. The only primary button is `Page.cta`.
- Components with `part` classes take a record of parts (a part cannot appear outside its component or twice).
- `dropdown` and `tooltip` are fields on leaves, not nodes. No `Raw Html` constructor. Ever.
- `Leaf.Calendar` delegates to `alexbruf/elm-cally` (a pure-Elm port of the Cally web component: same
  markup, same `part` attributes, light DOM, no ports). elm-cally's `Config` is built inside `Render`
  from the closed `CalendarConfig`, never exposed — the same rule `Daisy.Chart` follows for elm-charts.
  Its state lives in the app: `Daisy.Render.initCalendar*` / `updateCalendar`, `Daisy.Tree.setCalendarValue`.
  `TwoMonths` wraps its two `Month.view` grids in a container of Render's own (`grid grid-cols-1
  sm:grid-cols-2 gap-4`, all four already in `tokens`), because neither elm-cally nor daisyUI styles
  `[part~=months]` — upstream Cally leaves multi-month layout to the page. Grid, not flex: daisyUI's
  `.cally calendar-month { width: 100% }` would make flex items each claim a whole line. See
  `docs/tree-decisions.md` "Calendar via elm-cally" section 7.
- `Shell.Dashboard` renders as `drawer` + `drawer-open` at `lg:` with `menu` in the side and `navbar` on top.

## Render conventions

- All spacing/layout Tailwind tokens live in one constant table `Daisy.Render.tokens : List String` (gap, grid-cols, padding, height per size, icon size, and the two surface tokens `bg-base-200` / `shadow-sm`). RenderPurityTest asserts every emitted class is in `Schema.allClasses` or `tokens`, and `tools/render-class-audit.js` asserts every entry is a named `token*` constant with no daisyUI class in it. Before adding one, check `tests/RenderPurityTest.elm`'s `forbidden` list — `rounded-box`, `border`, `shadow-md`/`-xl` and the opacity variants are there on purpose and that list is not to be edited to make room. 47 entries today.
- Surfaces are the renderer's job, not the caller's: `card` and `stats` emit `bg-base-100 shadow-sm`, the dashboard `drawer-content` and the plain `<main>` emit `bg-base-200`, and `navbar` emits `p-4` (the same gutter as the content column, so an `indicator-item` cannot overhang the viewport). daisyUI paints none of these itself; its own docs examples add them as utilities.
- `Leaf.Icon` emits no daisyUI class at all, only a `size-*` token. Path data lives in `Daisy.Render.Icons`, which stays out of `elm.json`'s `exposed-modules`; `Daisy.Icon` is data only. heroicons is a `devDependency` of `demo/` used to copy the `d` attributes once — never a runtime dependency.
- Overlays render after sections, order: drawer, modal, toast, inside one fixed wrapper.
- Chart colors are `var(--color-primary)` etc. via `Daisy.Chart.SemanticColor`. Chart height is fixed per block size token.

## Tooling rules

- Use `bun`/`bunx`, never npm/npx. Node scripts in `tools/` run with `bun`.
- `elm-format` everything Elm. `elm make` must produce zero warnings for `src/`.
- `tools/gen-cally-css.js` reads elm-cally's stylesheet out of `Cally.Css.stylesheet` (elm-cally 1.1.0+),
  preferring `~/.elm/0.19.1/packages/alexbruf/elm-cally/<newest>/src/Cally/Css.elm`, then the checkout at
  `~/elm-calendar/elm-cally/src/Cally/Css.elm`, then the old root `cally.css` for 1.0.0. It decodes the
  Elm triple-quoted literal and, when the checkout is present, byte-compares the result against that
  repo's `cally.css`, so a stale generated module fails rather than changing the demo silently. The
  source it used is recorded in the generated header. `elm.json` asks for `alexbruf/elm-cally 1.x`,
  which covers both. 1.1.0 is now published (package.elm-lang.org lists 1.0.0 and 1.1.0), so the
  package-cache path is the one that is used and a clean CI checkout resolves the demo's pinned
  1.1.0 from the registry with no local checkout involved.
- Playwright uses the system Chrome: `channel: "chrome"` (no browser download needed). Run headless.
- Do not write to `vendor/daisyui`. Do not hand-edit `src/Daisy/Schema*.elm`; change `tools/gen-schema.js` and regenerate.
- No `Html.Attributes.class`/`classList`/`attribute "class"` outside `src/Daisy/Render.elm`. No `Html`/`Html.Attributes`/`Svg` imports under `demo/src`.
- Never `cat` or read the dotenv file directly in shell commands (a hook blocks it); there are no secrets in this project anyway.
- CI order (`tools/ci.sh`): gen-schema diff → elm make → package-docs → elm-review → elm-test → render-audit → should-not-compile → gen-cally-css → demo build → css-coverage → Playwright. Any failure stops.
- `package-docs` is the `elm publish` gate: `elm make --docs=<tmp>` (every exposed module needs a module comment with `@docs` for everything it exposes) plus `elm-format --validate src`. The package name in `elm.json` must equal the GitHub repo, `alexbruf/elm-daisyui`; `tools/gen-schema.js` rewrites only `exposed-modules` and leaves the name alone.

## Commands

```

bun tools/gen-review-classes.js    # regenerate review/src/SchemaClasses.elm from fixtures/schema.json (needed by the NoRawSchemaStrings elm-review rule; run after gen-schema.js)
bun tools/extract-corpus.js        # docs -> fixtures/corpus/*.json
elm make src/Daisy/Render.elm --output=/dev/null
elm-test
bun tools/gen-corpus-elm.js        # fixtures/corpus + fixtures/rejected.md -> tests/Corpus/Fixtures.elm, tests/Corpus/Rejected.elm
bun tools/gen-cally-css.js         # demo/cally-base.css + demo/cally-daisy.css for Leaf.Calendar. Both are COMMITTED; the generator is authoritative, never hand-edit them
bun tools/render-class-audit.js    # static half of RenderPurityTest: no daisyUI class literal in Render.elm
cd review && elm-test              # rule tests
elm-review                         # from repo root, reviews src/
cd demo && elm-review --config ../review   # reviews demo/src (and src/Daisy/* via demo's ../src source dir); or `bun run review` from repo root does both plus regenerating SchemaClasses.elm
bun tools/should-not-compile/run.js
cd demo && bun install && bun run build
bun tools/css-coverage.js          # grep built CSS for Schema.allClasses
bun tools/build-docs-site.js       # markdown -> demo/dist/docs/*.html (runs automatically after `vite build`)
cd e2e && bunx playwright test
elm make --docs=/tmp/docs.json    # the elm publish docs gate
elm-format --validate src
bash tools/ci.sh                   # everything, in order
```
